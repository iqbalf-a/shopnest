Bagian 1

PRD

Apa yang dibangun, untuk siapa, sampai batas mana, dan bagaimana dummy data ditukar dengan API asli nanti.

1.1 Tujuan

ShopNest hari ini adalah API tanpa wajah — dinilai lewat Postman. Frontend ini mengubahnya jadi produk yang bisa dibuka, diklik, dan dipahami dalam dua menit oleh orang yang tidak akan pernah membaca kode Java-nya.

Tujuan utama

Satu alur belanja yang utuh dan jujur: cari produk → keranjang → checkout → lihat riwayat order. Bukan galeri komponen.

Tujuan kedua

Menunjukkan bahwa frontend paham batas service: harga adalah snapshot, stok milik product-service, identitas datang dari token.

Bukan tujuan

Bukan kloning Tokopedia. Tanpa pembayaran sungguhan, tanpa rekomendasi, tanpa chat, tanpa ongkir.

1.2 Keputusan: repo baru

Repo terpisah — sesuai arahanmu, dan memang pilihan yang tepat di sini. Alasannya bukan sekadar "beda project", tapi tiga hal konkret:

  • Siklus rilis beda. Frontend akan di-deploy puluhan kali sehari saat styling; backend jarang. Satu repo berarti setiap commit CSS ikut memicu build Maven tujuh modul.
  • Toolchain tidak bertemu. shopnest adalah repo Maven murni — .gitignore-nya tidak mengenal node_modules, dan tidak ada satu pun file JS di sana. Menyelipkan Node di dalamnya mengaburkan identitas repo backend yang sekarang rapi.
  • Dummy data dulu. Fase pertama tidak menyentuh backend sama sekali. Menyandera frontend di repo backend memaksa orang meng-clone tujuh service hanya untuk mengubah warna tombol.
Syarat agar repo terpisah tetap murah

Satu risiko nyata dari dua repo: kontrak API bisa melenceng diam-diam. Tambal dengan dua kebiasaan — simpan tipe TypeScript di satu file src/api/types.ts yang hanya mencerminkan DTO backend (lihat §1.6), dan salin docs/schema.sql serta brief ini ke repo frontend sebagai referensi beku. Kalau backend berubah, tipe ini yang pertama diperbarui.

1.3 Framework: React + TypeScript + Vite

Pertanyaan sebenarnya bukan "React atau Vue", tapi "perlu server rendering atau tidak". Bentuk backend ShopNest sudah menjawabnya.

Rekomendasi: SPA dengan Vite — bukan Next.js

ShopNest mengautentikasi lewat header Authorization: Bearer, bukan cookie. Next.js baru berguna kalau server bisa ikut membaca sesi — dan server Next tidak bisa membaca token yang disimpan di browser tanpa kamu memindahkannya ke cookie, yang berarti mengubah backend. Hasilnya: hampir semua halaman tetap jadi client component, tapi kamu menambah satu runtime Node di depan gateway yang sudah jadi satu-satunya pintu. Lapisan tanpa imbalan.

1.4 Scope v1

Batas dipilih dari apa yang benar-benar didukung backend hari ini. Semua yang di kolom kanan bukan "malas" — melainkan belum ada endpoint-nya.

Masuk v1

  • Daftar & masuk, simpan sesi, keluar
  • Katalog: daftar, pagination, filter kategori, pencarian nama
  • Detail produk + indikator stok
  • Keranjang sisi klien (tambah, ubah jumlah, hapus)
  • Checkout → POST /api/orders
  • Riwayat order + detail item
  • Batalkan order berstatus PENDING
  • Profil: buat, ubah, kelola alamat
  • Panel admin sederhana: CRUD produk

Ditunda

  • Pembayaran — tidak ada endpoint ke status PAID
  • Ongkir & kurir — alamat tersimpan tapi tidak dipakai order
  • Upload gambar produk — tabel products tidak punya kolom gambar
  • Wishlist, ulasan, rating — tidak ada tabelnya
  • Refresh token — backend hanya menerbitkan satu access token
  • Keranjang lintas perangkat — tidak ada tabel cart

* Katalog belum bisa dibuka tanpa login — dan ini bertentangan dengan niat produknya

Gateway mewajibkan token untuk semua path kecuali /api/auth/ dan /docs/specs/. Artinya GET /api/products pun menolak pengunjung anonim, sehingga halaman / dan /p/:id praktis tidak bisa dilihat sebelum login — padahal untuk toko, katalog yang bisa dijelajahi tanpa daftar itu justru corong utamanya.

Fase dummy tidak akan menyadari ini karena MSW melayani semuanya. Jangan bangun halaman katalog dengan asumsi anonim sampai backend memutuskan. Uraiannya di §1.8 poin 8.

Rute admin sekarang dijaga backend — bukan hanya disembunyikan

ProductController memeriksa X-User-Role pada POST, PUT, dan DELETE; selain ADMIN dibalas 403. Menyembunyikan menu berdasarkan role dari token tetap keputusan UX, tapi kini ada guard di belakangnya — memanggil POST /api/products langsung dengan token USER tidak lagi berhasil.

Konsekuensi praktis saat menguji: belum ada cara membuat akun ADMIN lewat API. Pendaftaran selalu menghasilkan USER, jadi panel admin hanya bisa dicoba dengan akun yang role-nya diubah langsung di database. Lihat §1.8 poin 7.

1.6 Kontrak API yang harus ditiru

Ini bagian terpenting untuk strategi dummy: data palsu harus berbentuk persis seperti data asli, sampai ke nama field dan bungkus response-nya. Semua di bawah disalin dari DTO backend, bukan dikarang.

Amplop response — seragam di keempat service

// setiap response, sukses maupun gagal, dibungkus ini
type ApiResponse<T> = {
  success: boolean
  message: string      // "Products found", "Invalid email or password", …
  data: T | null        // null saat error
}

// khusus daftar produk, data-nya dibungkus lagi
type PageResponse<T> = {
  content: T[]; page: number; size: number
  totalElements: number; totalPages: number; last: boolean
}

Tipe domain

type AuthResponse = {
  accessToken: string; tokenType: "Bearer"

  name: string; description: string | null
  price: number       // BigDecimal(15,2) → JSON number, mis. 149000.00
  stock: number; category: string
}

1.7 Strategi dummy data

Prinsipnya satu: komponen tidak boleh tahu bahwa datanya palsu. Kalau ada satu saja if (isMock) di dalam komponen, penukaran nanti jadi pekerjaan ulang.

Lakukan — cegat di lapisan jaringan

MSW mendaftarkan service worker yang menjawab fetch ke /api/*. Kode aplikasi tetap memanggil fetch("/api/products") seperti biasa.

// src/mocks/handlers.ts
http.get("*/api/products", ({ request }) => {
  const url = new URL(request.url)
  const page = Number(url.searchParams.get("page") ?? 0)
  // filter + potong halaman dari array dummy
  return HttpResponse.json({
    success: true, message: "Products found",
    data: { content, page, size, totalElements, totalPages, last }
  })
})

Hindari — dummy di dalam komponen

Pola ini terasa cepat di hari pertama dan mahal di minggu ketiga: status loading tidak pernah teruji, error tidak pernah muncul, dan setiap komponen harus disentuh saat pindah ke API asli.

// jangan
const products = DUMMY_PRODUCTS
if (loading) …  // tidak akan pernah true
if (error) …    // tidak akan pernah terjadi

Isi data dummy yang layak

  • 24–30 produk di 5–6 kategori, cukup untuk menguji pagination default backend (size=10) sampai halaman ketiga.
  • Harga rupiah yang realistis: 15.000 sampai 4.500.000 — menguji apakah layout tahan angka panjang. Sertakan satu produk 1.250.000,50 untuk membuktikan desimal tidak dibulatkan sembarangan.
  • Tiga kondisi stok: habis (0), menipis (1–5), aman. Ketiganya punya tampilan berbeda di §2.6.
  • Order di ketiga status, termasuk satu PAID — walaupun UI belum bisa membuatnya, riwayat harus siap menampilkannya.
  • Satu order dengan 8 item dan satu dengan 1 item, untuk menguji ringkasan yang panjang dan yang pendek.
  • Deskripsi produk kosong di beberapa entri — description boleh null di database.

Rencana penukaran ke API asli

  • Ganti VITE_API_BASE_URL dari kosong (MSW) ke http://localhost:8080.
  • Hentikan pendaftaran worker MSW di main.tsx — satu blok if (import.meta.env.DEV && USE_MOCKS).
  • Pastikan origin dev-mu terdaftar di shopnest.cors.allowed-origins pada gateway (§1.8 poin 1). CORS-nya sudah ada, tapi hanya http://localhost:5173 yang diizinkan secara default.
  • Jalankan ulang seluruh alur dan bandingkan: bentuk response harus identik dengan dummy. Selisih apa pun berarti §1.6 yang salah, bukan komponennya.

Handler MSW tidak dibuang setelah itu — pindahkan ke test. Mereka jadi fondasi pengujian komponen tanpa menyalakan tujuh service.

1.8 Celah backend yang mempengaruhi frontend

Delapan hal yang ditemukan saat membaca kode. Tidak satu pun menghalangi fase dummy, tapi semuanya akan muncul di hari penyambungan. Diurutkan dari yang paling pasti menggigit.

Pembaruan: poin 1 dan 2 sudah ditutup di backend (commit fef6384–2bf3924 di dev) dan dibiarkan di sini dengan catatan hasilnya, bukan dihapus — nomor poin tidak berubah supaya rujukan lama tetap sahih. Poin 7 muncul akibat perbaikan itu; poin 8 celah lama yang baru ketahuan saat memeriksa ulang kode.

1 · CORS — sudah diperbaiki

Dulu: pencarian cors di seluruh Java dan properties tidak menghasilkan apa pun, sehingga setiap request dari localhost:5173 ditolak browser — termasuk login, karena Content-Type: application/json memicu preflight OPTIONS yang datang tanpa header Authorization dan dibalas 401 oleh filter JWT.

Sekarang: CorsWebFilter ada di api-gateway/.../config/CorsConfig.java. Preflight dari origin terdaftar dibalas 200 beserta Access-Control-Allow-Origin/Methods/Headers dan Max-Age: 3600; origin tak terdaftar tetap ditolak. Karena CorsWebFilter berjalan di lapisan WebFlux, ia menjawab preflight sebelum JwtAuthFilter sempat memeriksa token.

Yang masih perlu kamu lakukan: origin dev diambil dari properti shopnest.cors.allowed-origins, default http://localhost:5173. Kalau Vite kamu jalan di port lain, atau frontend sudah dideploy, daftarkan origin itu — kalau tidak, gejalanya identik dengan CORS yang belum ada sama sekali.

2 · Order, profil, dan alamat orang lain — sudah diperbaiki

Dulu: id di path tidak pernah dicocokkan dengan X-User-Id. Cakupannya ternyata lebih luas dari yang tertulis di versi pertama dokumen ini — bukan tiga endpoint, tapi tujuh, dan tiga di antaranya operasi tulis: PATCH /api/orders/{id}/cancel (membatalkan pesanan orang lain), POST dan DELETE /api/users/{userId}/addresses/….

Sekarang: semuanya membandingkan id di path dengan X-User-Id dari gateway dan membalas 403 kalau tidak cocok. Pada cancel, pengecekan terjadi sebelum status diubah — pesanan korban tetap PENDING.

Yang berubah untuk frontend: asumsi "order bersifat privat" sekarang boleh dipakai. Tambahkan penanganan 403 (lihat tabel status di §1.6) — dan perlakukan berbeda dari 401: 403 bukan sesi habis, jangan logout.

3 · Status PAID tidak punya jalan masuk

Enum-nya ada, tapi satu-satunya transisi yang terpasang adalah /cancel. Artinya v1 tidak boleh menampilkan tombol "Bayar" yang tidak melakukan apa-apa. Tampilkan PENDING apa adanya, dan siapkan tampilan PAID untuk data yang masuk dari luar.

  • 4 · Tidak ada refresh token. Satu access token dengan masa berlaku dari jwt.expiration. Saat kadaluwarsa, satu-satunya jalan adalah login ulang — rancang penanganan 401 sebagai "sesi habis, masuk lagi", bukan percobaan diam-diam.
  • 5 · Produk tidak punya kolom gambar. Tabel products hanya menyimpan teks dan angka. Design system menjawab ini dengan thumbnail huruf berwarna (§2.5) — pilihan desain yang sadar, bukan placeholder abu-abu.
  • 6 · Keranjang tidak ada di backend. Sepenuhnya milik klien sampai tombol checkout ditekan. Konsekuensinya harus jujur di UI: keranjang hilang kalau ganti perangkat, dan harga di keranjang bisa basi — muat ulang harga saat halaman checkout dibuka.
  • 7 · Tidak ada cara membuat akun ADMIN. AuthServiceImpl selalu mengisi Role.USER saat registrasi, dan tidak ada endpoint untuk menaikkan role. Sejak guard admin dipasang (lihat catatan di akhir §1.5), konsekuensinya: panel admin tidak bisa diuji lewat API sama sekali — perlu UPDATE users SET role='ADMIN' langsung di database, atau backend menambahkan seeding admin. Rancang panel admin seperti biasa, tapi jangan jadwalkan demonya sebelum ini beres.
  • 8 · Katalog tidak bisa dibaca tanpa token. JwtAuthFilter.PUBLIC_PATHS hanya berisi /api/auth/ dan /docs/specs/, jadi GET /api/products membalas 401 untuk pengunjung anonim. Ini bukan akibat perbaikan kemarin — sudah begitu sejak Phase 1, tapi tidak pernah terlihat karena pengujian selalu memakai token. Keputusannya ada di backend: kalau katalog memang mau publik, tambahkan GET /api/products ke PUBLIC_PATHS (hanya GET, jangan seluruh prefix). Sampai itu terjadi, rute / dan /p/:id harus diperlakukan sebagai rute terlindungi.

1.9 Definition of done & urutan kerja

Selesai berarti

  • Setiap halaman punya empat wajah: loading, kosong, error, terisi
  • Semua harga lewat satu fungsi format — tidak ada toLocaleString yang berserakan
  • Form menolak input yang pasti ditolak backend, sebelum request dikirim
  • 401 di mana pun mengakhiri sesi dengan bersih
  • Terbaca di 375px — checkout termasuk
  • Navigasi keyboard sampai tombol checkout tanpa jebakan fokus
  • Kedua tema terang dan gelap terbaca

Urutan yang disarankan

  • M1 · Fondasi — Vite, token dari Bagian 2, primitif Button/Field/Pill, layout
  • M2 · Katalog dummy — MSW, grid, filter, pagination, detail
  • M3 · Sesi — login/daftar, simpan token, rute terlindungi
  • M4 · Belanja — keranjang, checkout, riwayat, pembatalan
  • M5 · Profil & admin — alamat, CRUD produk
  • M6 · Sambungkan — cek origin di CORS gateway, matikan MSW, uji ulang penuh termasuk jalur 403
Bagian 2

Design system

Token, komponen, dan pola domain. Halaman ini memakai token yang sama dengan yang didefinisikannya — apa yang kamu lihat di bawah adalah hasil nyatanya.

2.1 Tiga prinsip

Angka adalah bintangnya

Ini toko. Harga, stok, dan total adalah informasi yang dicari orang. Semua angka pakai tabular-nums agar berbaris rapi, dan harga selalu punya bobot tipografi lebih besar dari nama produk di sekitarnya.

Warna dipakai untuk status, bukan dekorasi

Hijau, kuning, dan merah hanya berarti stok dan status order. Indigo hanya berarti "ini bisa diklik". Kalau semua berwarna, tidak ada yang menonjol saat stok habis.

Tanpa foto, tetap punya wajah

Katalog tanpa gambar produk mudah terlihat seperti spreadsheet. Jawabannya bukan kotak abu-abu, melainkan thumbnail huruf berwarna yang konsisten per kategori.

2.2 Tipografi

Dua keluarga saja, dan keduanya dari rumpun yang sama: Geist untuk semua teks, Geist Mono untuk kode dan label. Tanpa serif — hierarki dibentuk oleh ukuran, bobot, dan tracking, bukan oleh pergantian wajah huruf. Keduanya tersedia di Google Fonts, jadi tidak ada aset yang perlu di-host sendiri.

2.6 Pola khas ShopNest

Tiga aturan yang tidak bisa ditebak dari komponen generik — semuanya lahir dari cara backend ini bekerja.

Uang

// satu-satunya tempat harga diformat di seluruh aplikasi
export const rupiah = (n: number) =>
  new Intl.NumberFormat("id-ID", {
    style: "currency", currency: "IDR",
    minimumFractionDigits: 0, maximumFractionDigits: 0
  }).format(n)          // 1250000 → "Rp 1.250.000"
Jangan pernah menghitung total yang mengikat di klien

Backend menyimpan numeric(15,2) dan menjumlahkan dengan BigDecimal. JavaScript menjumlahkan dengan float biner. Total di halaman keranjang adalah perkiraan untuk pengguna; angka yang berlaku adalah totalAmount yang dikembalikan POST /api/orders. Tampilkan angka dari server itu di layar konfirmasi, jangan tampilkan hasil hitungan sendiri.

Order

  • Harga di detail order tidak boleh ditautkan ke katalog. order_items.price adalah salinan saat transaksi. Beri keterangan kecil "harga saat pemesanan" agar pengguna tidak bingung melihat selisih dengan halaman produk.
  • Tombol batal hanya muncul pada PENDING. Status lain tidak menampilkannya sama sekali — bukan menampilkannya dalam keadaan mati.
  • createdAt datang tanpa zona waktu (LocalDateTime → "2026-09-11T10:14:03.221"). Jangan serahkan ke new Date() begitu saja dan berharap benar; perlakukan sebagai waktu lokal server dan tampilkan apa adanya dalam format Indonesia.
  • ID order adalah UUID. Jangan tampilkan utuh di daftar — potong delapan karakter pertama dan sediakan salin-ke-clipboard di halaman detail.

2.7 Responsif & aksesibilitas

Titik henti

  • 375–639 — satu kolom; grid katalog 2 kolom; ringkasan checkout pindah ke atas tombol
  • 640–1023 — katalog 3 kolom; filter jadi baris chip yang bisa digeser
  • ≥ 1024 — katalog 4 kolom; filter jadi sidebar tetap; checkout dua kolom

Wajib dipenuhi

  • Target sentuh minimal 44×44 — termasuk tombol +/− jumlah
  • Fokus terlihat di semua kontrol (garis brand-600, offset 2px)
  • Status tidak pernah hanya lewat warna: selalu ada teks
  • Perubahan jumlah keranjang diumumkan lewat aria-live
  • Thumbnail huruf bukan informasi — beri aria-hidden
  • Hormati prefers-reduced-motion
